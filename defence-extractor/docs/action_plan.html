Causes found in run c

  • Agents too large for the 8k context. Roles (Lapua failed), attribution (owners fell to 0.6 confidence, so 19 correct values on the heat-meter brochure ended unresolved), references and audit overflowed: they carry registries and fact lists that the chunk settings did not bound.
  • An old evidence-check bug. A value whose unit is printed in its label was grounded on its number and then rejected by the final check: 3,288 values in the old weak-set runs on OpenRouter too, which explains part of the low Lapua and copper-alloy scores.
  • A reused footnote marker. '*' meant "rotors turning" under one table and "General Electric CT7-2E1" under the next; only the first legend was kept, and the 27B verifier rightly called the facts ambiguous.
  • Model differences. The farm model retypes values (fixing a typo) and named one entity "SHARKY 774 / SHARKY 775".

Fixed for run d

  • Roles fall back to the entity types instead of failing the document; each role call carries only its own registry slice.
  • Attribution, references, audit and verification split an input that does not fit the window; batch sizes are settings.
  • The evidence check accepts units printed in labels ("sec:", "in.......", "WEIGHTS, lbm", "m / sec").
  • Each marker use binds to its nearest legend; joined model names become one entity per model; retyped values are re-anchored to the printed text. 61 unit tests.

What testing uncovered

Fixed this round

  • OCR never ran on the server. The OCR runtime was missing and the layout library expects a newer OCR package than exists. Scanned pages were read by the vision model alone. Per-page routing would have sent every PDF with one scanned page to plain-text parsing (no tables, no headings). Fixed, and a failing page window now degrades only its own pages.
  • The farm's 27B accepts 8,192 tokens per request (prompt, reasoning and answer together). Our prompts were sized for 32k. Answers came back cut off or empty. The gateway now gives each answer what the prompt leaves, splits inputs that do not fit, and the farm uses smaller chunks (settings in .env).
  • Forced thinking used up the answer budget, so the page map came back empty. A thinking allowance and a retry with a larger budget fix it.
  • One failed call failed the whole document (Lapua). The page map now falls back per window to roles from scope and value density.
  • OCR misreads codes (M90RP17 for M9ORP17), which splits a product in two. Vision stays first on image pages; the OCR text is the fallback.

What it means

  • The engine's accuracy so far was measured on OpenRouter with 32k+ contexts. On the farm, with 8k and forced thinking, each call sees less context and more calls are needed, so the farm results mix code changes with farm limits. Compare runs on the same endpoint.
  • Silent failure was the common thread: OCR, the context window and the page map each failed without anything in the output saying so. That is why the plan below puts "never fail silently" first.

Point 4: handling every PDF challenge

Your reasoning is right; the method needs one change. With more than 2 lakh PDFs (about 1.8 million pages at our average of 8.8 pages per file), "build it when we see it" fails: a problem absent from all 250 sample files can still sit in up to 1.2% of the corpus, about 2,400 files. But "implement a full solution for everything" is not the goal either. Some problems cannot be solved, only detected and reported (password-protected files, handwriting, redactions). Every handler also runs on the good files, and an untested one breaks them; this round showed it, since per-page OCR routing would have degraded about one PDF in eight (every file with a page lacking a usable text layer) because OCR was broken. Expensive handlers (vision) must fire only where needed, because the farm is the bottleneck.

The method: detect everything, measure, handle by impact, never fail silently.

  1. Detect. The scanner (dx pdf-scan) flags 48 challenges per file and page from the PDF itself, at about 180 pages per second on CPU. Done.
  2. Measure. Run it over the 2 lakh corpus: 1 to 3 hours on the server's CPUs, no GPU. The prevalence numbers set the build order.
  3. Handle in three tiers. Handle: full handling for common or costly problems. Route to vision: a page the text layer cannot represent goes to the page-image route. Detect and report: problems that cannot be solved get an explicit status.
  4. Test. Every handler gets a generated test PDF and real examples from the scan; the guard set stops regressions.
  5. Report. Every result says which challenges were found and how each page was read, and files with high-risk flags go to a review list.

Build order for the open items

Six work packages. Within each, items go in order of prevalence from the 2 lakh scan. Each item ships with a test PDF and must pass the guard set.

1. Never fail silently (first)

  • A safe fallback for every agent, so one failed call degrades a part, never the document
  • Page routes and challenges found, recorded in every result
  • Review list for files with high-risk flags or a non-ok status
  • Evaluation per challenge: generated test PDFs plus real examples

2. File level (small, deterministic)

  • Non-PDF files routed by content; password files reported
  • Repair pass for damaged files
  • XFA text, form-field values, embedded attachments
  • Duplicates processed once; document date and revision on every fact

3. Text clean-up

  • Word-validity check in the text-quality score
  • OCR language by script; OCR vs vision number cross-check
  • Superscripts (m², ×10⁶, footnote markers) from character geometry
  • Look-alike letters, letter spacing, full-width characters, watermarks, markings

4. Document modes

  • Tenders: requirements kept apart from product specifications
  • Manuals: technical-data sections only
  • Slides; bilingual files merged by language version
  • Skip contents, legal and blank pages before extraction

5. Layout and tables

  • Reading-order check, sidebars, rotated text, paragraph continuation
  • Tiles for tiny type and oversized pages; infographic regions to vision
  • Header lineage, merged row labels, shared variant columns, option matrices
  • Borderless and dense tables re-read from the page image

6. Meaning and values

  • Version and year conditions, footnote conditions, negation
  • Acronym dictionary, cover-image product names
  • Number formats by language, ambiguous units, calibre notation
  • Evidence boxes and table cells in the output; visual check of image-read numbers

Point 6: orchestration that calls agents per task

Today

  • Every document runs the same 16 stages in order, with a checkpoint after each.
  • A stage that fails stops the document (seen on Lapua); each agent handles its own retries differently.
  • Chunk sizes assume a 32k-token endpoint; the farm needs settings in .env.
  • Nothing records which pages were read how, or why a part was skipped.

Proposed

Scan→Plan→Run tasks→Check→Assemble→Report
  • Plan per document, built by rules from the scan and profile: document mode (product sheet, catalogue, news, tender, manual, slides, not a product document), a route per page (text, OCR, vision, skip), which agents run, and the budget per task.
  • Agent contracts: goal, inputs, output schema, checks in code (ids exist, quotes are in the evidence, owners are valid), retry policy (larger budget, then split the input, then thinking on) and a safe fallback output.
  • Task status: ok, degraded (with reason), skipped (with reason) or failed. A document never fails because one task failed when a fallback exists.
  • Endpoint profile (context window, thinking switch, parallel slots, speed) sets chunk sizes automatically.
  • Observability: time, tokens, retries, splits and fallbacks per task; plan versus what actually ran.

Why rules decide the plan, not a planning model. At 2 lakh documents the plan must be predictable, cheap and testable. The signals it needs are deterministic (the scan, the profile), and an extra model call per document would add farm load and a new way to fail. The model is used where judgement is needed: inside the agents, and to classify a document only when the rules are unsure.

  1. Task status and a fallback for every agent (the page map has one now).
  2. Endpoint profile replaces the per-endpoint chunk settings.
  3. Document plan from the scan, recorded in the result.
  4. Agent contribution analysis on past runs: which agents' facts survive verification and at what token cost. Expensive agents run only for the document modes where they pay off, and prompts shrink to what each agent needs (smaller prompts are faster on the farm).
  5. Per-task observability and a run report by challenge.

Rule for shipping a change

  • The guard set does not lose more than one fact and wrong-product values do not rise.
  • The weak set rises, or the change is neutral there and needed elsewhere.
  • Re-runs reuse cached answers for every stage the change does not touch, so a change to a late stage re-runs in minutes.

Limits of small sets

  • A few pages understate problems that grow with document size, such as finding models in a 300-page catalogue; the full sets cover that.
  • With 83 facts, a change of two or three facts is noise.
  • Compare runs on the same endpoint: farm results include its limits.

Throughput for 2 lakh PDFs

The farm configuration is the main blocker for the corpus, more than any PDF challenge. About 1.8 million pages at the 5,600 completion tokens per PDF page our corpus run used (thinking mostly off) is about 10 billion tokens; with forced thinking, closer to 16 billion. At one request at a time and about 50 tokens per second, that is roughly 6 to 10 years. With continuous batching (vLLM or SGLang) a 27B model typically serves well over 1,000 tokens per second per GPU: about 110 GPU-days for 10 billion tokens, or two weeks on eight GPUs. Page triage (skipping contents, legal and blank pages) and switching thinking off cut it further.

Estimates from our own runs; the batching rate is an assumption to confirm on the farm's GPUs.
