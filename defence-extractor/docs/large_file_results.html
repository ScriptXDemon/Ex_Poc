Can the large-file test set run now?

Yes. All 15 documents run end to end through the Temporal pipeline, with no page limit: the parser reads PDFs in 40-page windows (294 pages for the largest), image pages are transcribed, long stages heartbeat and resume from checkpoints, and a per-document spend cap protects the budget. 14 documents have finished. The largest, a 294-page L3Harris radio catalogue (9,407 blocks, 1,218 entities, 1,197 product-keyed table rows), is still in its extraction stage and will be added to this page when it completes. On the documents the old run also processed, recall rose from 61% to 77%, and the end of documents improved most: 41% to 71%.

Specs outside the catalogue, on the right product

What the engine accepted

6798 specifications were accepted on these documents: 15% map to a catalogue parameter, 18% to a candidate parameter from the A14 extension, and 68% are dynamic, named from the document's own label. Among the answer-key specs the engine found, 45 were dynamic parameters on the right product; 14 dynamic values landed on a wrong product.

How a value is tied to its product

  • The product map gives every section its product from headings, page titles, running headers and the page map, and the extraction prompt shows it next to each section ("describes: …").
  • Rows and columns of product-keyed tables (one row or column per model) are assigned to that model without asking the model.
  • Each call sees only the 40 entities relevant to its pages, not a list of hundreds.
  • A part's values (controller, battery, camera, launcher) stay on the part and roll up into the product's sheet as a subsystem.
  • The verifier checks every accepted value against its evidence and owner.

Vision with the same Qwen 27B

How it works

  • Routing is per page: only pages with no text layer, or mostly image with little text, are rendered (1,600 px long side) and transcribed. The text layer stays the source of truth everywhere else.
  • The model returns typed blocks (heading, table row, label–value, paragraph), inserted in reading order on their own page, so every later agent reads them in place.
  • Values read from images get a lower evidence confidence and go through the same verification.
  • At most 40 pages per document; about $0.002 per page on OpenRouter.

Result

The IWI US catalogue has 32 pages; 28 are mostly image and 19 have no text layer. All 28 went through vision; 10 carried technical content and gave 116 blocks, and 353 of the 364 candidate facts came from them, attached to the item numbers of the product list (XB17-9, GAR1651, M9ORP17…). The engine found 35 of the 37 key facts, including the values that exist only in the images of the product list; the old run produced nothing for this file. On the other PDFs vision only fills gaps: 20 blocks from 1 of 3 image pages in the propulsion catalogue, 23 from 1 of 16 in the forum catalogue, and nothing where the pages are photos.

What changed

Planned changes D1–D8

  • D1 product mapSection, page and table ownership before extraction; windowed page map over the whole document.
  • D2 local entitiesAt most 40 relevant entities per call instead of the whole registry.
  • D3 full PDFs40-page windows with a disk cache, no page limit; tables continued across a page break keep their header.
  • D4 visionPage-level transcription of image pages with the main model.
  • D5 checkpointsHeartbeats from long stages, per-document spend kept on disk, finished calls replayed from the cache.
  • D6 product sheetDuplicates merged, conflicting values flagged, page provenance, subsystems rolled up.
  • D7 spend orderSpecification-dense chunks first, so a budget cap cuts narrative, not tables.
  • D8 answer keysPosition-aware partial keys for the 15 documents, written blind.

Found and fixed while testing

  • hyphensThe verifier model writes non-breaking hyphens; every such value failed the evidence check (204 in the old run).
  • table units"IMU: 259; Units: mm" read as "259 mm" was rejected; about 2,900 such table values in the old run are now kept.
  • rolesProduct-type entities left without a role lost their values from the output; re-asked, typed, kept.
  • partsNamed parts in spec tables become components of their product; a section label no longer pulls a part's values onto the product.
  • throughputAttribution and parameter mapping ran one call at a time, and mapping overflowed on catalogues; both now batch in parallel.
  • PDF threadsThe PDF library is not thread-safe; parallel documents now share one lock.
  • scoringProduct names must agree on model numbers, so variants such as M322 and M338 are told apart.

Cost, time and capacity

This run

$8.79 for the 14 finished documents, from $0.002 (the news listing without specs) to $2.72 (the Lapua catalogue, 1,514 blocks); none reached its $3 cap. The 294-page catalogue runs under a $5.50 cap. About 2,000 model calls, all served by one provider (DeepInfra): median latency 69 s, 90th percentile 203 s with 48 calls in parallel. Retries and JSON repairs were 33% of the spend: with thinking off the 27B returns an empty list on 47% of entity-finding calls on the big PDFs and 22% of extraction calls, and each is retried with thinking.

For the data centre

In the data centre these retries cost GPU time instead of money; your note that thinking on/off retries are affordable holds, but on documents over 100 pages it is cheaper to start entity finding with light thinking than to pay for the empty first answer. Load also needs to spread: here one provider queue set the pace, so on our own servers run several replicas behind the router. Large catalogues are dominated by output tokens (extraction and audit answers of 5–9k tokens), so size GPU capacity for generation, not prompt length. The per-document cap stays as a guard against a runaway file.

Still weak, and next

  • Entity discovery on catalogues. The copper-alloy catalogue registered 27 entities for dozens of alloys, so whole alloy pages had no product. Stopping the product map from carrying the previous alloy across an unknown model heading lifted it from 16 to 22 of 55 and cut wrong-product values from 6 to 3; next, promote model-number headings (C7451, RF-7850A…) to products.
  • Roles on long news logs. The role model labels many real products “other” (66 of 127 on the Arleigh Burke log). Their values are now kept in the output, but the product map and attribution do not see them yet; map “other” to the role implied by the entity type.
  • Spec cards with labels and numbers in separate blocks (Lapua: “Muzzle velocity”, “m / sec”, “910”) lose values: 12 of 26 found. A layout rule that joins label, unit and number would fix most.
  • Throughput. Spread calls over several replicas and start entity finding with thinking on big PDFs; together they should halve the time of a run like this.
  • Bigger evaluation set. These keys sample 403 specs on 13 documents; the larger set you are preparing will narrow the error bars, especially for the middle of documents (65% now).
