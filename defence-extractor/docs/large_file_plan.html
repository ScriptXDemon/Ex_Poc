What happens to a large document today

The engine already reads documents in section-aligned chunks that carry their heading path, caps dense chunks, splits answers that overflow, and closes the evidence ledger, so nothing is silently dropped. The problems are in the parts that need the whole document at once.

Is the current model choice enough?

For reading a bounded chunk, yes. Qwen3.8-27B finds 97% of benchmark specs and 91% on the corpus answer keys, and most misses trace to what the chunk could see, not to the model's reading ability. Keep it as the high-volume extractor.

For the document-wide decisions, it should be tested against a bigger model. Large files fail on decisions that need the whole document: which product a table belongs to, roles among hundreds of entities, a page map over 400+ sections. I want to run those steps (A2, A4, product map, A6, A7) with Qwen3.5-122B-A10B: a mixture-of-experts model with about 10B active parameters, so it serves at close to 27B speed, with a 262k context and image input. Keep gpt-oss-120b for audit and verification; it is cheap and did well.

A longer context window is not the fix. Putting a whole 300-page catalogue in one prompt costs more and blurs which product a value belongs to. The fix is structural: map the document to products first, then extract each product's pages with only that product's context (D1, D2 below).

A/B test design

  • Same pipeline and prompts; only the document-wide steps switch model.
  • Run on the 6 test documents with the most ownership errors.
  • Adopt the 122B for those steps if values on the wrong product drop by a third or more, at acceptable cost and latency.
  • Also check whether the 122B avoids the 27B's empty answers with thinking off (retried today; 12–19% of LLM cost).

At data-centre scale (per document, run average)

  • Main model: about 29k input and 13k output tokens.
  • Verifier: about 15k input and 11k output tokens.
  • Output tokens dominate GPU time. Per million corpus-like pages that is about 13B output tokens on the main model and 11B on the verifier; documents over 30,000 characters weigh 5–10 times an average one.
  • The local registry (D2) and product-segmented reading (D1) cut input tokens on large files the most.

PDF structure, OCR and vision

Measured on all 250 corpus PDFs (2,203 pages): 69 pages (3.1%) have no text layer, 250 (11.3%) are mostly image with little text, 103 PDFs (41%) have at least one such page, and 37 have them on 30% or more of their pages. The IWI 2020 catalogue is 32 pages with 28 image-heavy pages and only about 3,800 characters of text. Many of these images are product photos, but some carry spec tables and annotated drawings that the engine cannot see today.

Proposed routing (per page, not per file)

  1. Text layer present: Docling layout and tables, as now. This stays the source of truth for verbatim values.
  2. No text layer: OCR that page (RapidOCR inside Docling), even when the rest of the file has text.
  3. Mostly image: one vision call that transcribes any technical text and tables on the page into blocks, tagged with page and source vision.
  4. Table that parses badly (Docling's own cell-alignment warnings, ragged rows): re-read the table from the page image and compare.

Why vision is an add-on, not the main path

  • Nearly 89% of pages carry their content in the text layer, which gives exact characters for evidence quotes.
  • Vision output is read, not quoted, so its values get a lower evidence confidence and are checked again by the verifier.
  • Both Qwen3.8-27B and Qwen3.5-122B accept images, so no extra model is needed in the data centre.
  • Cost is small: about $0.002 per page image on OpenRouter.
